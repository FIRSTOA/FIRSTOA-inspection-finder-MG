## 0. 먼저 알아 둘 공통 사실 (모든 항목에 걸림)

1. **FIELD 는 아직 사용자 단위 권한이 없다.** [사실] 앱은 공개 anon 키로 Supabase 를 읽고 쓴다(src/supabase.ts). 그룹웨어 SSO 는 켜졌지만 "2단계 RLS(사람별 권한)"는 미착수. 그래서 카톡 전문·이카운트 매출처럼 **민감한 데이터를 새 표에 넣으면, anon 으로 select 를 막고 엣지 함수(서비스 키 + SSO 확인)로만 읽게** 해야 한다. 다른 표처럼 anon select 를 열면 앱 번들을 아는 누구나 다 읽는다. D2·D3 의 가장 큰 전제다.
2. **카운터를 모으는 길이 이미 네 갈래다.** [사실]
   - 한조·틴텍(외부 원격 관리): 점검 양식 "한틴이카유무" 칸, 접수 "한조/틴텍코드"(H123 / T456), 물류 양식 "한조셋팅완료"(한조·모바일한조·한조공유기·설치불가).
   - 이메일 카운터: 복합기 → count@firstoa.co.kr → 네이버 hee2gwang·hee3gwang, 어사이드가 매일 10시 정리해 카톡(DB 저장 없음, AGENTS.md).
   - 카운터 문자전송: 관리부 마감 목록(봇이 마감방에서 수집 → counter_sms_inbox → 2분 cron → counter_sms_targets) → 직원이 고객에게 사진 요청.
   - 현장 점검 매수: jeomgeom "매수" 칸 + [매수 분석](counter-ocr, 사진 → 숫자).

   **[사실, 오늘 읽기 전용 실측]** 2026-04-01 이후 점검 5,905행 / 업체 3,086곳 중 "한틴이카유무" 값이 있는 2,681곳의 최신 값: 한조 735 · 한공(한조 공유기로 추정) 499 · 한조해지 29 · 모바일한조 16 · "유" 907(무엇이 있다는지 불명) · 한유 78 · 설치불가 64 · 무 53 · 단순마감 40 등. 즉 **표기가 분명한 한조 계열만 약 1,250곳(값 있는 곳의 47%)** 이다. 이메일카운터를 이 칸에 적은 곳은 거의 없다(이 칸에 이메일 여부를 따로 적지 않는 듯 — [확인 필요]).
   그래서 E1·E2·E3 는 따로 보면 안 되고 **"기기별 카운터 원장 하나"** 로 묶어 설계해야 효과가 난다(5절 추천 1번).
3. **카톡 자동화 금지 규칙** [사실]: 자동 발송은 KST 10시 이후·야간 22~08시 금지(봇·노트북 모두), 카톡 PC 는 Ctrl+A·Ctrl+F·WM_SETTEXT 금지·열린 창에만 붙여넣기(tools/kakao-pc), 메신저봇R 은 두 스레드가 동시에 JS 를 돌리면 죽는다(수집은 "리스너는 큐에만 넣고 폴링 스레드가 보낸다" 패턴 — gas-and-bot/supabase-outbox-poller.js ⑧). 카톡 쪽 수정은 전부 방지훈(kakao-pc-rules) 검사 대상.
4. **외부 팀 데이터는 보는 창으로만** [사실, 2026-10-03 사용자 지시]: 남이 운영하는 원본을 우리 Supabase 로 복사하지 않는다. 한조·이카운트·관리부 자료도 "누구 것인가"를 먼저 정해야 한다.

## D2 (15) 카톡 DB — 카톡 내용을 전부 DB 로

**① 원하는 것** 업무 카톡방 대화를 한 곳(DB)에 모아 검색·집계·에이전트 근거로 쓰기.

**② 지금 있는 것**
- [사실] 메신저봇R 수집 통로: supabase-outbox-poller.js ⑧ — onMessage 에서 마감방 글만 큐(_listQueue)에 담고 폴링 스레드가 counter_sms_inbox 로 POST. 같은 틀에 "업무방 글 전부" 큐를 하나 더 붙이면 된다. 방 이름은 room_map(관리 탭 카톡방 매핑, 현재 26행: AS 5·점검 5·재계약 5·미수 4·불만 3·자가·부품·초과조정·마감 각 1)에서 읽는 방식이 이미 있다.
- [사실] 카톡 TXT 파서: apps-script/first-data/src/Kakao.gs parseKakaoMessages_ — 세 형식(대괄호형 "[이름] [오후 3:24] 내용", 점 날짜형 "2024. 1. 5. 오후 3:24, 이름 : 내용", 년월일형) + 날짜 띠를 이미 읽는다. msgHash_(방|날짜|작성자|본문 MD5)로 같은 TXT 를 다시 올려도 새 글만 처리. 불만·미수·재계약·해지방어·경영지원 방은 OpenAI 로 레코드 추출(KAKAO_SOURCES). 지금은 사람이 TXT 를 올리는 방식.
- [사실] room_activity(봇이 보낸·본 방 40개), 노트북 카톡 PC(봇 계정, 방 36개 열기 검증).

**③ 가능성: 조건부 가능** — 텍스트·업무방 한정이면 쉽다. "전부"는 어렵다.
- 막히는 지점
  - **봇은 알림으로 읽는다** [추정, 메신저봇R 구조상]: 봇 계정이 들어가 있고 알림이 켜진 방만 보인다. 알림 끈 방·봇이 없는 방·개인 대화는 못 본다. 폰이 꺼지거나 봇이 죽은 동안의 글은 영영 빠진다(되감기 없음).
  - **사진·파일은 못 받는다** [추정]: 알림에는 "사진" 같은 자리 글만 온다.
  - 아주 긴 글이 알림에서 잘리는지 [확인 필요] — 마감 목록(긴 글)은 지금 받아지고 있어 대체로 괜찮아 보인다.
  - 과거분·빠진 구간은 **카톡 PC/폰 "대화 내보내기" TXT** 로 메워야 한다. 방마다 사람이 메뉴를 눌러야 한다. 노트북 카톡 PC 로 자동화하려면 새 메뉴 경로 클릭이 필요한데 지금 금지 규칙(눈먼 UI 조작 금지)과 충돌 → **자동 내보내기는 비추천**, 월 1회 사람 내보내기 + 업로드로. 내보내기 형식은 PC·안드로이드·아이폰·버전마다 조금씩 달라 샘플로 확인 필요 [웹] — 기존 파서가 세 형식을 다 받으므로 큰 문제는 아닐 것.
- 저장량 [추정 계산]: 방 40개 × 하루 60건 × 평균 200바이트(한글 약 70자) ≈ 하루 0.5MB → 연 180MB, 인덱스·원문 포함 **연 0.3~0.5GB**. Supabase Pro 기본 DB 디스크 8GB [웹] 안에 들어간다. 사진은 제외(넣으면 지금 사진 저장소처럼 월 GB 단위 — 현재 사진이 월 약 1.3GB 증가). 실제 하루 글 수는 [확인 필요] — 1단계 1주 수집 뒤 실측으로 바꾼다.
- 방 범위 제안: **1단계 = room_map 에 등록된 업무방(26개)만.** 팀 잡담방·개인방·외부 고객방 제외. 방 추가는 관리 탭에서 사람이 켜는 "수집 허용" 표시로.

**④ 가장 작은 첫 단계(1~2일)**
1. 표다빈: kakao_messages 표 설계(room, sender, sent_at, text, source bot/export, hash 유일, has_media, created_at). **anon 은 insert 만, select·update·delete 불가**(outbox 와 반대). 읽기는 엣지 함수만. 주민번호 모양(6자리-7자리)은 넣을 때 트리거로 가림. 보관 기간 cron(예 1년).
2. 구현: 봇 스크립트 ⑨ — room_map 업무방 글을 큐 → 폴링 스레드가 묶어서 POST(⑧ 과 같은 패턴). 방지훈 검사, poller-harness 시나리오 추가. 봇폰 스크립트 통짜 교체 필요.
3. 1주 시험 수집(테스트 전용방 + 사용자 팀 방 1~2개) → 하루 건수·용량 실측.
4. (다음) 과거분: Kakao.gs 파서를 TS 로 옮긴 업로드 화면, 같은 hash 규칙(방·분 단위 시각·작성자·본문)으로 봇 수집분과 합침.

**⑤ 필요한 결정·자료**
- D2-1 어느 방까지(제안: room_map 업무방만, 단계적 확대).
- D2-2 보관 기간(제안 1년, 대표·법무 판단).
- D2-3 누가 읽을 수 있나(제안: 팀장 + 본인 팀 방만 — 정확히 하려면 SSO 2단계 권한이 먼저).
- D2-4 직원 고지: "업무 카톡방 글을 회사 시스템에 저장한다"를 공지할지.
- 자료: 방별 PC 내보내기 TXT 샘플 1개(형식 확인용, 개인정보는 지워도 됨).

**⑥ 위험**
- **개인정보** [법률 판단 확인 필요]: 업무방 글에도 고객 이름·전화·주소, 개인 고객 주민번호(거래처 코드 칸에 129곳 — customer-hierarchy.md 실측), 직원 사적 대화가 섞인다. 수집 목적·보관 기간·접근 권한을 정하고 직원에게 알리는 것이 안전하다. 봇 계정이 그 방의 참여자라 "제3자 감청"과는 다르다고 보는 게 일반적이나 [추정], 회사 규정으로 정리할 일.
- **보안**: anon select 를 열면 전 대화가 사실상 공개 — 반드시 막는다(0절 1).
- **약관**: 메신저봇R 같은 비공식 자동화는 카카오 운영정책상 계정 제재 위험이 있다 [웹]. 이미 봇을 쓰고 있어 위험이 새로 생기진 않지만, 봇 폰 1대 의존(단일 장애점)이 더 커진다.
- **유실**: 봇 수집은 빠지는 구간이 생긴다. "전부"를 약속하지 않는다 — 화면에 "봇 수집(빠질 수 있음)" 표시.

**⑦ 효과(추정)**
- 직접 시간 절감은 작다. Kakao.gs TXT 업로드를 사람이 하던 것이 자동이면 월 2~4회 × 10~15분 ≈ **월 1시간**(업로드 빈도 [확인 필요]).
- 큰 효과는 간접: 통합 검색 360 의 entity-ask 가 "기록에 없습니다 — 카톡방 원문 확인"이라고 답하던 빈칸(지시문에 그렇게 적혀 있음)이 메워진다. E5 에이전트의 재료.

## D3 (20) 이카운트 자료 자동 수집

**① 원하는 것** 이카운트(ERP)의 거래처·매출·수금·카운터 자료를 사람 복사 없이 FIELD 로.

**② 지금 있는 것**
- [사실] 재계약 화면(src/recontract/ledger.ts)이 이카운트 **거래처관리대장 I(거래명세서별)** 를 Ctrl+A·Ctrl+C 붙여넣기로 받아 적요(계약 이력)·판매/수금·카운터 누계·초과를 해석한다. 회귀 테스트 fixture 있음(tests/fixtures/ecount-ledger-*.txt).
- [사실] 그 화면은 **일부러 저장하지 않는다** — "이카운트 매출·수납 데이터라 기기에 남기지 않습니다, 탭 닫으면 삭제"(public/guide/recontract.html). 즉 지금 원칙은 "매출 데이터는 FIELD 에 쌓지 않는다".
- [사실] 2026-10-10 로드맵에서 "이카운트 API" 는 팀장 결정 대기 항목 중 하나.

**③ 가능성: 조건부(원하는 자료에 따라 갈림)**
- [웹, 확인 필요] 이카운트는 **OPEN API** 를 제공한다. 인증은 회사코드 + 사용자 ID + **API 인증키**(ERP 안에서 발급, 테스트 키 → 검증 후 실사용 키) → Zone 조회 → 로그인으로 SESSION_ID 를 받아 요청마다 붙이는 방식으로 알려져 있다. 호출 횟수·간격 제한이 있다.
- [웹, 확인 필요] 제공 API 는 **입력(저장) 계열이 중심**(품목·거래처 등록, 판매·구매·견적·주문 입력 등)이고 조회는 재고·품목 등 일부로 알려져 있다. **거래처관리대장 같은 회계 출력물 조회 API 는 없을 가능성이 높다 [추정].** 재계약에 필요한 건 바로 그 대장이다.
- 그러면 남는 길:
  - (가) **엑셀 내보내기 → 노트북 감시 폴더 → 자동 적재**(반자동). 이카운트 목록 화면 대부분에 엑셀 내보내기가 있다 [웹]. 사람이 월 1회 내보내기만 하면 나머지는 자동. 현실적.
  - (나) 브라우저 자동 조작(로그인·메뉴 클릭) — 약관·보안·화면 변경에 약함. **비추천.**
- 막히는 지점: 저장 원칙(②)과 권한(0절 1). 인증키 발급 권한은 마스터(관리부·대표) 쪽일 것 [추정].

**④ 가장 작은 첫 단계(1일, 개발 0)**
1. 이카운트 관리자 화면에서 **API 인증키 발급 메뉴와 API 목록 문서**를 열어 캡처(또는 목록만 적어 주기) → 대장 조회 가능 여부 판정.
2. "거래처관리대장"을 **여러 거래처 한 번에 엑셀로** 내보낼 수 있는지 확인(지금 파서는 한 거래처 화면 복사 기준).
3. 둘 다 안 되면 붙여넣기 방식을 유지하고 D3 는 보류.

**⑤ 필요한 결정·자료**
- D3-1 이카운트 매출·수금 데이터를 FIELD DB 에 **저장해도 되는지** — 지금 원칙을 바꾸는 일. 대표·관리부 결정.
- D3-2 데이터 주인(관리부?) 동의(0절 4).
- D3-3 API 인증키를 누가 발급·보관할지(키는 노트북 환경 변수·Supabase 비밀값에만).
- 자료: API 목록 캡처, 엑셀 내보내기 샘플 1개.

**⑥ 위험** 매출·수납은 회사 기밀 — anon 공개 구조에 저장하면 사고. 인증키 유출 시 ERP 쓰기(입력 API)까지 열릴 수 있음 → 조회 전용 사용자로 발급 가능한지 [확인 필요]. 브라우저 자동 조작은 약관 위반 소지.

**⑦ 효과(추정)** 재계약 방문 준비에서 대장 찾기·복사가 한 업체 2~3분이라 가정, 분기 방문 대상 팀당 약 24곳(가이드 예시 "분석됨 2/24") × 5팀 ≈ 120곳 → **분기 4~6시간**. 대장 조회 API 가 없으면 (가) 반자동이라 그 절반 정도.

## E2 (17) 복합기 한조 대체 프로그램

**① 원하는 것** 한조(외부 원격 관리)가 하는 일을 자체 프로그램으로 대신하기.

**② 지금 있는 것 / 한조에 대해 알 수 있는 것**
- [사실] 저장소 흔적: 기기마다 "한조/틴텍코드"(예 H123 / T456), 설치 때 "한조셋팅완료"(한조·모바일한조·한조공유기·설치불가), 점검 "한틴이카유무"(한공·한조·모바일한조·한조해지업체·보안으로 설치불가·고객불편으로 설치불가·무), 원격 접수 탭 L열 "한조처리", 임대리스트 코드 칸 "한조X·한조설치X" 153행.
- [추정] 이 흔적으로 보면 한조는 **고객사에 프로그램(PC 설치형) 또는 전용 공유기를 두어 복합기 카운터·상태를 원격으로 모으는 서비스**이고, 틴텍(T 코드)은 비슷한 다른 업체 것이다. "보안으로 설치불가"는 고객 PC·망에 설치가 필요하다는 뜻으로 읽힌다. 원격 처리(L열)까지 한조가 맡는지는 불분명.
- [확인 필요] 한조가 회사 이름인지 제품 이름인지, 비용 구조(대당 월 요금?), 관리 화면(웹 콘솔) 유무, 우리가 받는 결과물(엑셀·메일·화면) — 웹에서 확실한 정보를 찾지 못했다. 사내 담당자 확인이 필요하다.
- [웹] 대체 기술의 기본: 복합기는 대부분 **SNMP** 를 지원하고 표준 Printer-MIB(RFC 3805)로 총 카운터·소모품 잔량을 읽을 수 있다. 흑백/컬러 구분 카운터는 제조사 전용 MIB 이 필요한 경우가 많다. 즉 "고객사 안에서 SNMP 로 읽어 인터넷으로 올리는 작은 프로그램"이 한조 핵심과 같은 구조일 것 [추정].

**③ 가능성: 어려움(전체 대체) / 부분은 가능**
- 막히는 지점: 고객사마다 망 안에 수집기(PC 프로그램·소형 기기)를 깔아야 한다 → 설치·보안 승인·고장 대응이 1,000곳 규모의 운영 일. 제조사별 OID 차이, 원격 제어는 별도. 개발보다 **현장 배포·유지가 본체**.
- 부분 대체: 카운터만 보면 **E1 이메일 카운터가 이미 "설치 없는 대체"** 다(복합기 자체 기능). 한조 해지·설치불가 업체를 이메일 카운터로 옮기는 게 가장 싸다.

**④ 가장 작은 첫 단계(1일, 개발 0~0.5일)**
1. 한조 담당자에게 ⑤ 질문 확인.
2. (선택) 사무실 복합기 1대로 SNMP 시험: 노트북에서 총 카운터·토너 잔량을 읽어 보는 짧은 스크립트 — "우리가 직접 읽을 수 있나"의 증거만. 고객사 배포는 하지 않는다.

**⑤ 필요한 결정·자료**
- E2-1 한조가 하는 일 범위(카운터 수집 / 소모품 경고 / 원격 제어 / 마감 자료 생성 중 무엇).
- E2-2 한조 비용(대당·월) — 대체 가치는 결국 비용으로 판단.
- E2-3 계약상 데이터 소유·해지 조건.
- E2-4 대체를 원하는 이유(비용? 데이터 접근? 품질?) — 이유가 "데이터를 못 본다"라면 E3 로 충분하다.

**⑥ 위험** 고객사 망에 우리 프로그램을 넣는 책임(보안 사고 시 회사 책임). 한조 계약 위반 소지. 개발자 1명(사용자) 의존 시스템이 늘어난다.

**⑦ 효과(추정)** 비용 절감이 핵심인데 금액을 모른다 → [확인 필요]. 개발·배포 공수는 최소 수개월로 추정. **지금은 권하지 않는다.**

## E3 (18) 한조를 읽어 카운터 정리 (E2 대신)

**② 지금 있는 것**

**④ 가장 작은 첫 단계(1일)**
1. 한조 관리 화면 계정을 가진 사람 확인 → 화면 캡처 몇 장(카운터 목록, 다운로드 단추 유무).
2. 다운로드 파일이 있으면 1개(시리얼·카운터 열만 남겨도 됨)를 받아 → 기획실이 열 매핑표와 "기기별 카운터 원장" 설계를 쓴다.

**⑤ 필요한 결정·자료** 한조 계정 보유자·로그인 권한, 샘플 파일, 관리부가 지금 한조 자료를 어떻게 쓰는지(마감 흐름), 데이터 주인.

**⑥ 위험** 한조 이용 약관(데이터 재사용·자동 로그인 금지 조항 여부 [확인 필요]). 계정 공유 시 보안. 원본과 어긋남(사본이 오래됨) → 가져온 날짜를 항상 표시.

**⑦ 효과(추정)** 마감 카운터를 사람이 옮겨 적는 일이 있다면 그만큼. 한조 업체 1,250곳 중 월 마감 대상이 30%, 한 곳 옮기기 1분이라 가정하면 **월 6시간 안팎**. 관리부 실제 작업 방식이 [확인 필요]라 폭이 크다. 덤으로 "기기별 카운터 추이"가 생겨 초과료·재계약 판단 근거가 된다(D3 대장 카운터와 교차 검증).

## E4 (19) 고객용 IT 프로그램

**① 원하는 것** 고객(거래처 직원)이 직접 쓰는 IT 도구 — 무엇인지 아직 미정.

**② 지금 있는 것**

- [사실] 고객에게 보내는 리포트(report-view 엣지, 점검리포트), 해피콜·홍보물 문자(솔라피).
- [사실] IT 파트 자료는 남의 프로젝트(IT 시트·Apps Script) — 고객용 IT 도구는 IT 파트 영역과 겹친다.

**③ 가능성: 조건부 — "무엇을"이 정해지지 않아 판단 불가.** 후보별 난이도(추정):

| 후보 | 난이도 | 재사용 |
|---|---|---|
| QR 찍으면 그 기기 정보로 AS 접수(로그인 없음) | 중 | 서비스접수 표·보류된 QR 설계 |

- 막히는 지점: 고객이 쓰면 **로그인 없는 공개 쓰기 경로**가 생긴다. 10/10 감사에서 "쓰기 엣지 함수 공개 호출"이 결정 대기로 남아 있다 → 장난·스팸 접수 방지(기기 QR 토큰, 횟수 제한)가 먼저.

**④ 가장 작은 첫 단계(0.5일, 개발 0)** 사용자·팀장이 위 표에서 1개를 고른다. 추천은 **"QR → 설명서 사이트의 그 기종 페이지 + [AS 접수] 단추"** — 설명서 사이트와 보류된 QR 접수를 QR 한 장으로 잇는 것(새 시스템 없이 기존 두 개 연결).

**⑤ 필요한 결정·자료** E4-1 무엇을 만들지, E4-2 고객에게 무엇을 보여도 되는지(계약·미수 정보 금지 등), E4-3 IT 파트와 범위 조정, E4-4 QR 스티커 인쇄·부착 주체.

**⑥ 위험** 공개 경로 남용, 고객 개인정보 노출, 고객 앞 장애(내부 도구보다 품질 기준이 높다), 회사 이름으로 나가는 문구 검수.

**⑦ 효과(추정)** QR 접수가 전화 접수를 대신하면 접수 1건 3~5분 → 1분. 규모는 고객 직접 접수 비율에 달림 [확인 필요]. 고객 만족·재계약 근거(정성).

## E5 (14) 회사 업무용 에이전트 (개발 에이전트 팀과 별개)

**① 원하는 것** 직원이 일하면서 묻고 맡기는 AI(데이터 질문, 미처리 요약, 독촉, 리마인드).

**② 지금 있는 것 — 이미 꽤 있다**
- [사실] entity-ask(업체 하나 기록만 근거, 출처·날짜 붙여 답), data-ask(허용 표·칸만 읽기 전용 도구 조회, 최대 8회 — 점검·AS·미수·초과·재계약·불만·접수·일정·부품·지식 문서 450편·플레이북 145편·처리이력 13,000건), okr-assist, playbook-draft, report-polish, AI 비용 기록(_shared/ai-usage).
- [사실] 카톡에서 부르는 질문 봇 틀: gas-and-bot/*-query-bot.js("?"·"/"로 시작하는 글 → 웹훅 → 답장, 허용 방만). 지금은 Make.com 웹훅으로 간다.
- [사실] 미처리 묶음 로직(src/homeUnhandled.ts), 일정 미처리(src/overdueLogic.ts), 재계약 다음 확인일 설계(recontract-next-check.md), 미수 방문이력(misu_visits).

**③ 가능성: 가능** — 재료가 다 있다. 새로 할 건 "어디서 부르나"와 "언제 알려 주나".
- 막히는 지점: 단체방에서 답하면 질문 안 한 사람에게도 데이터가 보인다 → 방별 허용 범위. data-ask 는 지금 앱(anon)에서 부르는 함수라 카톡에서 부르면 **누가 물었는지 확인이 약하다**. AI 비용(ai-usage 로 측정 가능). 환각 — entity-ask 처럼 "기록에 없으면 없다" 원칙 유지.

**④ 가장 작은 첫 단계(1~2일)** 둘 중 하나(둘 다 작다)
- (가) **아침 미처리 요약**: 평일 10:05 KST, 팀별 열린 접수·지난 일정·재계약 다음 확인일 도래분을 한 장으로 팀 방에(outbox). homeUnhandled 규칙 재사용, AI 없이 규칙만으로 먼저. 0건이면 안 보냄.
- (나) **카톡 "?질문" → data-ask**: 테스트 전용방 1개에서만, 답 끝에 출처 표기. Make.com 대신 Supabase 엣지 직접 호출.

**⑤ 필요한 결정·자료** E5-1 어느 쪽 먼저(제안: 가 — 위험이 적고 효과가 매일 보임), E5-2 받을 방·시간, E5-3 카톡 질문을 허용할 방, E5-4 월 AI 비용 상한.

**⑥ 위험** 단체방 정보 노출, 알림 피로(무시되면 소용없음), 카톡 발송 시간 규칙(10시 이후·야간 금지), 봇 계정 의존.

**⑦ 효과(추정)** 팀장·파트장이 아침에 접수·일정 화면을 돌며 확인하는 데 10~15분이라 가정 → 5팀 × 하루 10분 × 20일 ≈ **월 15시간 안팎**. 놓친 미처리 감소는 정성.

## E6 (21) 반복 업무 자동화 후보 찾기

**① 원하는 것** 회사 업무 중 자동화할 반복 일을 시간 많이 드는 순으로 찾기(웹·로컬, 어사이드·GPT·클로드 무엇으로든).

**② 지금 있는 것** [사실] 이미 자동화된 것: 마감 목록 수집, 키맨 포스터, 카운터 사진 전송, 백업, 카톡 중계, 매수 사진 읽기, 시트 동기화, 어사이드 이메일 카운터. 그리고 이 보고서의 D2·D3·E1~E5. 평가 기록(docs/eval/2026-Q4-worklog.md)에 "효과 숫자" 칸이 있어 측정 틀은 있다.

**③ 가능성: 가능(조사 일, 개발 아님)** 막히는 지점은 "현장 기사·관리부·영업이 실제로 무엇에 시간을 쓰는지" 자료가 없다는 것뿐.

**④ 가장 작은 첫 단계(1주 관찰, 개발 0)**
1. 관찰표(사람·업무·한 번 걸리는 시간·주당 횟수·도구(카톡/시트/이카운트/한조/메일)·손으로 옮겨 적기 여부) 한 장을 팀원에게 1주 적게 한다.
2. 시간 × 횟수 순 정렬 → 상위 10개를 이 보고서 형식(①~⑦)으로 판정.
- 관찰 전 가설(후보): 이카운트 ↔ 시트 손 옮기기, 마감 카운터 받기(E1·E3), 카톡 양식 → 시트 재입력(D2), 명세서·세금계산서 발송 안내 글(재계약방에 "명세서 SMS·이메일 발송 완료" 글이 반복 — Kakao.gs 필터 규칙에 그 예시가 있음), 초과료 계산, 방문 일정 짜기.

**⑤ 필요한 결정·자료** 관찰표를 돌릴 범위(CS팀만? 관리부·영업 포함?) — 다른 부서는 팀장 승인.

**⑥ 위험** 다른 부서 업무를 "자동화 대상"으로 적는 것 자체가 민감할 수 있다. 측정 없이 절감 숫자를 보고서에 쓰는 것(로드맵에서도 "가정 예시"라고 밝히기로 함).

**⑦ 효과** 직접 효과 없음. 다음 분기에 무엇을 할지 고르는 근거와 4분기 평가 보고서의 "측정된" 숫자.

## 5. 우선순위 표와 추천 순서

| 항목 | 판정 | 효과(추정) | 난이도 | 막는 것 | 첫 단계 크기 |
|---|---|---|---|---|---|
| E1 이메일 카운터 | 가능 | 중(이력 DB·마감 문자 축소, 월 ~7h) | 낮음(설계 끝남) | 대표 승인(IMAP/전달) | 1~2일, 승인 전 파서만 |
| E3 한조 읽기 | 조건부 | 중~높음(카운터 원천 약 1,250곳, 월 ~6h) | 낮~중(내보내기 있으면) | 한조 자료 형태·계정·주인 | 1일(확인·샘플) |
| E5 업무 에이전트 | 가능 | 중(월 ~15h, 매일 보임) | 낮음(재료 있음) | 방·시간 결정 | 1~2일 |
| D2 카톡 DB | 조건부 | 중(간접 — 360·에이전트 재료) | 중 | 개인정보·anon 읽기 막기·방 범위 | 1~2일 + 1주 시험 |
| D3 이카운트 | 조건부 | 중(분기 4~6h) | 중~높음 | 대장 API 유무·저장 원칙·매출 기밀 | 1일(API 목록 확인) |
| E6 반복 업무 찾기 | 가능 | 간접(다음 일 선정) | 낮음 | 관찰 협조 | 1주 관찰 |
| E4 고객용 IT | 조건부 | 미정 | 중~높음 | 무엇을 할지 미정·공개 경로 보안 | 0.5일(고르기) |
| E2 한조 대체 | 어려움 | 미정(비용 모름) | 높음(현장 배포) | 범위·비용·계약 | 1일(질문·SNMP 시험) |

**추천 순서 3개**
1. **카운터 통합(E1 + E3 → "기기별 카운터 원장")** — 카운터 원천 네 갈래(한조·이메일·문자 사진·점검 매수)를 시리얼 기준 한 표로. 이번 주 할 일: E3 한조 확인 질문·샘플 1개, E1 옛 지시서 복원 + 메일 샘플 파서(승인 없이). 이유: 원천이 이미 돌고 있어 개발이 작고, 마감 문자·초과료·재계약이 같은 숫자를 쓰게 된다. E2(대체)는 이 결과를 보고 판단.
2. **E5 아침 미처리 요약** — 재료가 다 있고 1~2일, 매일 눈에 보이는 효과. 규칙으로 시작해 신뢰가 쌓이면 카톡 "?질문"(data-ask) 시험방.
3. **D2 카톡 DB 1단계(업무방 26개, 텍스트, anon 읽기 막기)** — 단, 보관 기간·열람 범위·직원 고지를 먼저 정한 뒤. 이 데이터가 쌓여야 E5 가 "카톡방 원문 확인" 빈칸을 메운다.
- 병행(개발 0): E6 관찰표 1주, D3 이카운트 API 목록 확인 30분. 보류: E2·E4(무엇을/비용이 정해질 때까지).
