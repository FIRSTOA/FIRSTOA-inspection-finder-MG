## C3. 미처리 = 시트 상태 열 기준

### 1. 한 줄 목표와 쓰는 사람
서비스접수 미처리 현황판과 홈 "미처리" 칸이 **각 부서 접수 시트의 상태 열**(처리완료가 아닌 것 = 공란·진행중 등)을 미처리로 센다.
쓰는 사람은 대표·팀장(PC, 홈 관제 덱)과 CS 접수 담당(PC, 서비스접수 오른쪽 기둥)이다. 현장 기사는 쓰지 않는다.

**규칙 제안(한 함수, 모든 탭 공통)** — 새 순수 모듈 src/receptionSheetState.ts 의 sheetStateClass(value):
- **완료**: 글자에 완료·취소·중복·이관·해결·재접수가 들어 있거나, 공백을 뺀 값이 AS접수·A/S접수인 것. 이관·재접수·AS접수는 "다른 곳으로 넘어감 = 이 칸의 일은 끝"으로 본다.
- **보류**: 정확히 "보류". 미처리로 세되 배지를 따로 단다(지금 DB 현황판이 보류를 미처리로 세는 것과 같게).
- **미처리**: 그 밖의 전부. **공란**, 진행중, 처리중, 처리예정, 전달예정, 미처리, 부재중, 채널보냄, 문의중, "복귀후 카톡준다고함", 전자계약서미작성 등이 여기에 든다.
- 행 판정: 마커 열(영업·경영 B·D·E / 원격 B·D·J) 중 하나라도 값이 있어야 "행"으로 본다. 맨 끝의 순번만 있는 빈 줄(예: 해지방어 5880행)은 뺀다.

### 5. 데이터 설계 — 어디서 읽나

**결론: 시트에만 적힌 행까지 세야 하므로 시트를 직접 읽어야 한다.** DB에는 이 접수 시트들의 미러 표가 없다. churn_defense 같은 표는 카톡 양식 표라 이 시트와 다르다.

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 브라우저가 공개 CSV·gviz를 직접 읽음(itSheet.ts 방식) | SQL·엣지 없음 | 해지방어 탭 CSV가 3.7MB라 60초 폴링이 무겁다. 문서가 "링크 공개"일 때만 동작하고, 고객 전화번호가 담긴 시트를 공개에 계속 기대게 된다 |
| **B. 새 엣지 함수가 Sheets API로 읽어 미처리 행만 돌려줌(읽기 통과, 표 없음)** ← 제안 | 서비스 계정(field-sheet-sync가 이미 편집 권한으로 씀)으로 읽어 공개 링크와 무관하다. batchGet 1회로 3탭을 읽고, 응답은 미처리 수백 행이라 작다. 앞례로 contact-sheet-pull이 있다 | 엣지 함수 배포가 필요하다. 폴링마다 Google 호출이 생긴다(엣지 안 60초 캐시로 완화) |
| C. 미러 표 + cron(시트 → reception_sheet_rows) | 이력·KPI(C5)에 재사용, 홈이 빠름 | 새 표·RLS·cron SQL이 필요하다. 통째 교체 미러는 misu 사건(숨김·기록 소실)의 전례가 있다 |

**제안 = B(1단계), C는 C5 KPI 때 다시 판단.** C3에는 SQL이 필요 없다.

**엣지 함수 reception-sheet-open(새, 읽기 + 제한된 자가 치유)**
1. 탭 제목을 gid로 찾는다(sheets-api.ts spreadsheetMeta). 이름이 바뀌어도 동작한다.
2. batchGetValues(sheets-api.ts export 재사용)로 해지방어접수 A5:W, 경영지원접수 A5:Z, 원격 A1:W를 한 번에 읽는다.
3. 머리를 검증한다. 영업·경영은 G5 머리 "진행중/처리완료/보류/취소"(dept-sheet-spec normHeader 재사용), 원격은 G1 "처리여부"·L1 "한조처리"이다. 다르면 그 탭만 errors에 "시트 머리 변경: …"을 넣고 빼며, 나머지 탭은 계속 읽는다.
4. 각 행을 같은 규칙(Deno 쪽 사본 supabase/functions/reception-sheet-open/state.ts — vitest가 두 사본을 같은 표본으로 대조)으로 분류해 **미처리·보류만** 돌려준다.
   돌려주는 모양: { source: sales|mgmt|remote, kind: 영업팀|경영지원|원격이관|IT, sheetRow, seq, date(YYYY-MM-DD), author, handler, state, vendor, field, region, summary(접수내용 40자), receptionId? }.
   날짜는 C열 yyMM + B열 "M월 d일"로 만든다. C가 이상하면 날짜를 비우고 경과일을 계산하지 않는다(실측 1행).
5. **DB 연결(receptionId)**: 영업·경영은 field_sheet_sync_jobs(category reception_sales/mgmt, sheet_status=synced, 최근 120일)의 sheet_row와 _dupKey(dept:접수id:append)로 행 번호 → 접수 id를 잇는다. 그 행의 접수자(E)가 잡 author와 같을 때만 인정한다(행 밀림 방지). 원격은 service_receptions.sheet_row를 쓰고, 이번 달 접수이면서 R열 상호가 vendor 앞 6자를 포함할 때만 인정한다.
6. **자가 치유(복합기 healDoneReceptions와 같은 방식)**: 이어진 DB 행이 접수/진행중/원격대기인데 시트가 "완료"이면 service_receptions를 status=완료, completed_by="시트 처리완료 동기화"로 PATCH한다(조건에 상태를 다시 건다). 시트가 "취소"이면 취소로 한다. 한 번 부를 때 최대 50건이다. → 영업 DB 1행(세안이엔씨)이 바로 정리된다.
7. 엣지 안 메모리 캐시 60초, 응답은 { rows, fetchedAt, errors, healed }이다.
8. 고객 전화번호는 **돌려주지 않는다**(필요 열만).

**프런트 합치기 규칙**
- 영업팀·경영지원: **시트 행이 진실이다.** DB 지원 행 중 시트에 이어진 행(receptionId가 붙은 것)과 잡이 synced인 행은 DB 쪽에서 뺀다(중복 방지). 잡이 queued·failed·none인 DB 행만 DB 상태로 남긴다(앱에서 막 접수해 아직 시트에 안 간 건).
- 운영지원: 시트가 없다. DB 그대로이다.
- 원격이관·IT: 시트 행이 진실이다. DB 원격·IT 행 중 시트에 이어진 행은 뺀다. **이어지지 않은 DB 원격대기 행에만 기존 isStaleRemote(7일)를 남긴다**(월이 바뀌어 지난달 시트 행이 사라진 경우의 안전망). 시트에서 온 행에는 7일 규칙을 쓰지 않는다.
- 복합기 AS: 지금 그대로(DB + 일정 대조).
- 시트 읽기가 실패하면 그 종류는 **DB만으로** 보여 준다. 패널 위에 "시트를 못 읽어 영업·경영·원격 숫자가 빠졌을 수 있음" 한 줄을 띄운다(지금 syncError 자리 재사용). 숫자를 0으로 만들지 않는다.

### 6. 화면 흐름
1. 서비스접수 오른쪽 기둥 [미처리 현황] 또는 홈 "미처리" 칸을 연다.
2. 현황판은 DB 접수와 시트 미처리를 한 번에 읽는다(엣지 1회 + 기존 조회). 60초 폴링은 그대로이고, 엣지 캐시 때문에 시트 반영은 최대 약 1~2분 늦는다.
3. 종류별 칸 숫자는 시트 기준이다. 시트에서 온 행에는 작은 "시트" 배지와 상태 글자(공란은 "상태 비어 있음")를 단다.
4. 행을 누르면, DB에 이어진 행은 지금처럼 상세(DeptReceptionDetail·원격 펼침)로 간다. 이어지지 않은 시트 행은 **읽기 전용 카드**(업체·분야·접수일·처리자·내용 40자)와 [시트에서 열기](해당 gid, range=A행번호) 링크를 보여 준다.
5. 머리 안내는 "영업·경영·원격은 시트 상태 열 기준(처리완료·취소·이관이 아니면 미처리)"으로 둔다. "시트에 직접 적은 건은 안 나옵니다" 안내가 남아 있으면 지운다.
6. (D1 결과에 따라) 오래된 건은 "90일 넘음 n" 칩으로 따로 접어 둔다.

## C4. 서비스접수 검색에 부서명(임대리스트 Q열)

### 1. 한 줄 목표와 쓰는 사람

### 2. 지금 구조(코드 확인) — "검색 기준은 어디인가"
- **답: 임대리스트(서비스접수 시트가 아님).** 검색은 src/api.ts searchLeaseList(q) 하나다. 표는 vendor_info(임대리스트 미러, 23,288행, 월요일 GAS 동기화)이다.
- 순서대로 최대 30건을 모은다. ① _업체명 ilike(trgm 인덱스) → ② 자산번호 ilike(trgm) → ③ 4자 이상이면 기번 ilike(trgm) → ④ 숫자면 순번 eq. 승격 컬럼은 트리거 vendor_info_sync_search가 _raw에서 채운다(vendor-info-search.sql·reception-sync.sql).
- 호출처: ServiceReception.tsx runSearch(712행, 결과 줄 1660~1680행), DeptReceptionScreen.tsx 114행(결과 줄은 DeptReceptionForm.view.tsx의 DeptCandidateRow), 그리고 순번 재조회 2곳(ServiceReception 572·596행). 안내 글은 "임대리스트 검색 — 업체명 / 자산기번 / 순번"(ServiceReception 1645행, DeptReceptionForm.view 137행)이다.

### 3. 임대리스트 Q열 실측
- 임대리스트 탭(gid 1037918773) 2행 머리: P=거래처명, **Q=부서명/현장명**, R=특이사항.
- vendor_info에서는 **최상위 컬럼이 아니고 _raw 의 "부서명/현장명" 키에만 있다.** 승격 컬럼이 없다.
- 값: 23,287행 중 의미 있는 값 17,364, "-" 5,912, 빈칸 11, 고유 6,362종. 예: "평택P4-PH1 북SUP현장", "본사", "단기", "추가".
- 5자리 코드 3,149곳 중 990곳은 부서명이 2개 이상이다 → **부서명은 지점(5자리)보다 한 단계 아래(현장·층·부서)**이고 기기마다 붙는다.
- REST 실측: _raw->>부서명/현장명 ilike "*xyznotfound*"(전체 훑기, 인덱스 없음)가 **0.33초**로 동작했다. 결과가 있는 검색은 limit 30에서 일찍 끝난다. 메모리의 "JSONB 스캔 타임아웃"은 지금은 재현되지 않았다. 다만 그 교훈과 동시 접속을 생각하면 인덱스가 안전하다.

### 4. 데이터 설계(C4)
- **제안: SQL 1장(작음)** — 새 supabase/vendor-info-dept.sql
  - vendor_info에 생성 컬럼 "부서명" 추가: generated always as (nullif(nullif(btrim(_raw->>'부서명/현장명'), ''), '-')) stored. 키맨 컬럼(customer-report-send.sql 57행)과 같은 방식이라 GAS가 _raw만 바꿔도 따라온다. 트리거는 바꾸지 않는다.
  - 인덱스 vendor_info_dept_trgm: gin ("부서명" gin_trgm_ops), if not exists.
  - notify pgrst, 'reload schema'. 머리 주석에 재실행 안전 표시. 2.3만 행을 다시 쓰므로 실행에 몇 초 걸린다.
